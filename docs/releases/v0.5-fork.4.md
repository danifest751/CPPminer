# CPPminer v0.5-fork.4 — pool recovery, correct work switching and proof verification

This is the fourth release in the fork's v0.5 series. It includes the full pool and
miner reliability batch developed after v0.5-fork.3, together with all existing
CUDA, OpenCL and CPU optimizations from that release.

CPPminer is based on [1640675651/CPPminer](https://github.com/1640675651/CPPminer),
the Pearl/Quantus miner by @foolzhz. Development and release builds are maintained
in this fork; upstream submissions are made only when the fork owner chooses them.

## What changed since v0.5-fork.3

### 1. Pool sessions recover when the connection is no longer useful

- **Authorization deadline:** the pool must accept authorization within 30 seconds.
  An explicit rejection reconnects immediately; silence or unrelated responses
  cannot keep the authorization attempt alive indefinitely.
- **First-job deadline:** after accepted Pearl authorization, the pool has 30 seconds
  to supply a valid first job. Invalid notifications do not satisfy this deadline.
- **Submit replies are tracked individually:** each share is registered before it
  is sent and is acknowledged only by a response with the matching JSON-RPC ID.
  This also handles a pool that answers immediately while the sending thread is
  still returning from its send call.
- **Oldest outstanding share deadline:** if any submitted share has waited 60 seconds
  without a reply, the miner reconnects. Sending more shares, receiving newer replies
  or seeing unrelated traffic does not reset that share's timer.
- **Bounded tracking:** pending submit state is bounded, preventing unlimited growth
  when a pool reads submissions but never answers them.
- **Fee-pool fallback remains operational:** unsuccessful fee-pool handshakes count
  toward the existing three-failure fallback.

These checks detect a connected socket that has stopped doing useful protocol work,
as well as a socket that has actually closed.

### 2. TCP connections try all pool addresses within a fixed budget

Connection attempts use a shared 10-second budget across the resolved IPv4 and IPv6
addresses, reserving time for later addresses instead of getting stuck on the first
unresponsive address. Pool URI host/port lengths and port ranges are checked;
bracketed IPv6 addresses are accepted.

A failed write to a disconnected socket returns a send error instead of terminating
Linux mining through `SIGPIPE`. Pool deadlines and hashrate measurements use a
monotonic clock, so changing the operating system's wall clock does not alter them.

**Scope:** DNS lookup still uses the operating system resolver and is outside the
10-second TCP connection budget.

### 3. The newest valid job wins, including jobs received before mining starts

Pearl and Quantus now use one bounded pending-work slot. A newer valid job replaces
older pending work. Jobs received before authorization completes are retained and
become eligible for mining only after authorization succeeds.

Work publication and mining startup also coordinate cancellation: a newer job that
arrives between taking pending work and beginning a scan cancels the stale scan.
The same rule applies when a new job arrives during active mining. The miner no
longer needs separate raw-message and active-job queues to handle these transitions.

### 4. Work identity uses all relevant bytes

- **Pearl:** identity includes the pool job ID, complete header, effective target and
  resolved certificate version.
- **Quantus:** identity includes the pool job ID, complete mining hash, complete
  target and complete extranonce.
- A pool reusing a job ID with different work triggers a switch. A true duplicate
  is ignored. Equivalent hexadecimal casing does not create different work.
- Quantus current-job writes retain their destination array bounds, fixing a
  buffer overflow for long IDs and assembled job keys.

### 5. Pearl difficulty belongs to the connection and the received job

Pearl difficulty resets to 32 on each connection instead of carrying the previous
pool session's difficulty into a new session. A targetless notification receives
its difficulty snapshot and computed target when it arrives. A later difficulty
message cannot retroactively change that pending job's target.

Difficulty notifications accept normal JSON whitespace. Dispatch uses exact method
names. Invalid explicit targets, malformed headers, empty/oversized IDs and invalid
certificate versions are rejected before starting work. Object and supported legacy
array notification formats remain available.

### 6. JSON and authorization responses are validated strictly

The parser checks object/array grammar, delimiters, complete literal tokens, JSON
number syntax, UTF-8, Unicode escapes and surrogate pairs. Duplicate keys are rejected
after decoding, so `id` and an escaped spelling of `id` cannot provide two ambiguous
values. Network frame size and parsing depth remain bounded.

Valid escaped identifiers are decoded and accepted. Control characters that are not
suitable for protocol identifiers are rejected rather than truncated or interpreted
as hidden trailing data.

Authorization success requires boolean `true` or a successful object result. Numeric,
string and array results do not authorize mining. Objects with failed or malformed
status values, and responses carrying a non-null error, are rejected. Nested IDs and
unrelated notification fields cannot acknowledge an outstanding request.

### 7. Quantus login, sequence values and submission boundaries are corrected

- Login replies must match the outstanding login request ID. Explicit errors and
  failed statuses are rejected even when the response also contains a session or job.
- The latest early job is retained. Nested job notifications are supported.
- Login and initial-job waiting share a fixed 30-second deadline; unrelated traffic
  cannot extend it.
- `seq` is parsed directly as an unsigned 64-bit integer, preserving values above
  `2^53` and up to `UINT64_MAX`. Negative, fractional, exponential, overflowing and
  wrong-type sequence values are rejected.
- Present difficulty fields must be positive, finite JSON numbers.
- Immediately before sending a found nonce, Quantus rechecks cancellation, complete
  work identity and connection state. A disconnected session cannot start queued work
  or submit a nonce from stale work.

### 8. Gzip negotiation and failure handling match the pool protocol

Pearl enables gzip only from the authorize response's direct `type` field or the
result object's direct `type` field. The outer field takes precedence; unrelated
nested metadata cannot enable or override compression.

When the pool requires gzip, a compression or compression-buffer allocation failure
drops that proof instead of sending plain base64 in the wrong wire format. The proof
queue returns its buffers and can process subsequent shares. Pools that negotiate
plain proofs continue receiving plain base64.

### 9. Proof verification works in memory and covers targetless jobs

`--verify` checks the share's own header, proof and effective target directly in
memory. It also checks jobs whose notifications omitted an explicit target, using the
target computed when the job arrived. Failed verification prevents submission.

Normal mining and verification do not depend on writing temporary proof/header files
beside the executable. Cancellation is checked around proof construction and before
final submission, including after verification and gzip work, so stale proofs are
discarded rather than sent to the pool.

### 10. Dry-run diagnostics are separate for each process and job

`--dry-run` builds proofs without submitting them and saves the diagnostic pair beside
the executable:

```text
pp_<process-id>_<job-counter>_header.bin
pp_<process-id>_<job-counter>_proof.b64
```

Different processes and jobs do not share a fixed `pp_header.bin`/`pp_proof.b64` pair.
Open, write and close failures are checked and reported; a failed save is not reported
as a successful diagnostic result. This mode needs a writable executable directory.

### 11. Backend/resource failures terminate explicitly

Preparation, entropy-source, device/search, host-buffer, witness-transfer and proof
handoff failures propagate as a backend/resource error and terminate the miner with
status 1. They are distinct from cancellation by a new job and from exhausting a
configured nonce limit.

Quantus also checks failure of the entropy source used to prepare live nonce ranges.
A supervisor or restart script can restart a failed process instead of leaving it
connected and waiting silently for another job. Recreating a lost GPU context within
the same process is outside this release's recovery scope.

### 12. Command-line mistakes fail before mining starts

Unknown options, missing/empty required values, malformed or overflowing numbers,
partial device lists/dimensions and strings that would be truncated are rejected
before backend or pool startup. An option-name prefix is not accepted as a different
option. Value options also support `--option=value`.

`--threads 0` still selects automatic thread count; `--max-nonce 0` still removes the
nonce limit. Optional profiling counts are validated when supplied. The default pool
agent is now `cppminer/0.5-fork.4`.

## Verification

The reliability batch passed three CTest executables and 26 real-miner loopback
integration scenarios on Windows, Linux and a Linux CPU ASan/UBSan build. Coverage
includes real 30/60-second deadlines, authorization rejection, ACK correlation,
early/latest work, reused IDs, full work identity, gzip proof encoding, Quantus CPU
submission, targetless verification, CLI errors and concurrent dry-run artifacts.

Linux fault injection additionally confirmed status-1 exits when `/dev/urandom` is
unavailable during CPU preparation, host preparation or Quantus nonce preparation.

CMP50 CUDA hardware checks covered work identity, active-job cancellation and offline
mining with proof verification. A live gzip share from the updated miner was accepted
by HeroMiners. These checks do not establish a new speed measurement, nor hardware
validation of every supported GPU/backend. RTX 3090 hardware was not rented for this
release; extra CPU checking of Quantus OpenCL shares is outside this batch.

See [the local test instructions](https://github.com/danifest751/CPPminer/blob/v0.5-fork.4/docs/pool_reliability.md) for reproducing the checks.
Release packages are built locally; GitHub Actions are not required. Existing Windows
workflow smoke checks also stop on failed commands and run CTest when that workflow
is deliberately used in the future.

## Downloads and upgrade

- **`cppminer-win64-cuda.zip`:** Windows x64, CPU + CUDA + OpenCL, CUDA architectures
  `sm_75`, `sm_86` and `sm_89`. CUDA and MSVC runtime DLLs are included. A compatible
  GPU driver is still required.
- **`cppminer-linux-x64-cuda.tar.gz`:** Linux x64, CPU + CUDA + OpenCL, the same CUDA
  architectures, built on Ubuntu 24.04 (glibc 2.39). CUDA runtime is included; the
  operating system/GPU driver must provide the appropriate OpenCL ICD for OpenCL use.
- **`SHA256SUMS`:** checksums for the release archives.

Stop the old miner, unpack the new package into a new directory, and carry over your
wallet, pool, worker and desired backend settings. Configure the included start script
before launching. The old published binaries do not change when this release is
published; download the new archive to receive these fixes.

Quick CPU-only verification, without a wallet or pool:

```sh
cppminer --backend cpu --mock --mock-diff 40 --m 1 --n 1 --threads 2 --verify --max-nonce 4
```

On Windows use `cppminer.exe`. To check a supported CUDA card, replace `--backend cpu`
with `--backend cuda`. `--verify` can also be enabled during ordinary pool mining.

## Existing capabilities and developer fee

This release retains the Turing/Ampere/Ada CUDA kernels, RDNA3 WMMA path, Polaris/GCN
OpenCL kernel, CPU SIMD paths and Kryptex/HeroMiners gzip support from earlier fork
releases. It focuses on reliability and correctness; no new hashrate increase is claimed.

The existing 1% developer-fee mechanism and fork-maintainer fee destination are unchanged.
Fee cycles normally use HeroMiners; after three failed fee-pool attempts the existing
fallback uses the user's pool. `--no-fee` remains available. Upstream PRs are separate
from this fork release and are not created by publishing it.
